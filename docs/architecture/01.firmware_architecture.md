* Module Path: firmware/
* Target RTOS: Zephyr RTOS v3.7.0
* Supported Targets: NXP RW610 (Physical Silicon) | ARM Cortex-M33 (Renode & QEMU Emulation)
* Author: Bhushan (Embedded DevOps / Edge Platform Engineer)

## 1. Architectural Philosophy and Core Principles

In production appliance engineering (Whirlpool, KitchenAid, Bosch), firmware is never written as a single monolithic main.c file. Dumping hardware pin configuration, state machines, and timers into one file creates technical debt, breaks CI portability, and prevents automated testing.

Our firmware architecture is built upon 4 Foundational Principles:

1. Strict Separation of Concerns:
   * Business logic (10-speed calculation, soft-start ramping, thermal cutoffs) must have zero hardware knowledge. It must compile cleanly on host Linux, in QEMU, or on real silicon without changing a single line of code.
2. DeviceTree-Driven Hardware Abstraction (Zero ifdef in C code):
   * Switching between microcontrollers (Virtual Cortex-M33 vs. Physical NXP RW610) must never be done using messy ifdef VIRTUAL or ifdef PHYSICAL preprocessor directives.
   * All pin mappings, PWM timer channels, and button contacts are injected declaratively via DeviceTree Overlays (.overlay).
3. Deterministic Concurrency via RTOS Primitives:
   * Time-critical motor control is decoupled from slow I/O (UART printing, Wi-Fi telemetry) using separate Zephyr threads communicating through thread-safe Message Queues (k_msgq).
4. Declarative Tuning via Kconfig:
   * Mechanical parameters (ramp acceleration rate, control tick interval, thermal cutoff thresholds) are declared in Kconfig, allowing CI/CD to build specialized test variants without source edits.

## 4. Multi-Target Hardware Abstraction (DeviceTree Overlays)

How do we switch between our Virtual Cortex-M33 Renode Simulation and the Physical NXP RW610 Test Jig without changing one line of C source code?

We define generic DeviceTree Aliases in our code:
* mixer-motor: Node for the motor PWM gate.
* mixer-power: Node for the master ON/OFF button.

When building for STM32:
west build -b rw610_renode firmware/ automatically applies boards/rw610_renode.overlay.

When building for NXP RW610:
west build -b rd_rw612_bga firmware/ automatically applies boards/rd_rw612_bga.overlay.

## 5. RTOS Concurrency & Threading Model

To ensure motor timing is rock-solid and never interrupted by slow prints or Wi-Fi communications, firmware runs 3 Preemptive Threads:

````text
+-----------------------+     k_msgq      +-----------------------+
|  Input Scanner Thread | --> |  Motor Control Thread |
|  - Period: 50ms       | (slider_event)  |  - Period: 100ms (High) |
|  - Priority: 7 (Med)  |                 |  - Priority: 2 (High) |
+-----------------------+                 +-----------------------+
                                                      |
                                                      | k_msgq (telemetry_event)
                                                      v
                                          +-----------------------+
                                          |    Telemetry Thread   |
                                          |  - Period: 500ms      |
                                          |  - Priority: 10 (Low) |
                                          +-----------------------+
`

1. motor_control_thread (Priority 2 - Highest):
   * Deterministic 100ms cycle.
   * Processes soft-start ramp (+5% or -5%).
   * Calculates instantaneous RPM and updates PWM hardware.
   * Thermal safety check (>85 C) executed first every cycle.
2. input_scanner_thread (Priority 7 - Medium):
   * Runs every 50ms.
   * Debounces the Master ON/OFF power button.
   * Scans slider contacts PB0-PB10.
   * When a change occurs, sends an event into mixer_event_msgq.
3. telemetry_thread (Priority 10 - Lowest / Preemptible):
   * Pulls status snapshots from telemetry_msgq.
   * Formats structured serial log lines to USART2.
   * Cannot block or delay the motor control loop.

## 6. Declarative Tuning via Kconfig (firmware/Kconfig)

All operational constants are moved out of hardcoded defines and into Kconfig:
* CONFIG_APP_MAX_SPEED_LEVELS (default 10)
* CONFIG_APP_RAMP_STEP_PERCENT (default 5%)
* CONFIG_APP_RAMP_TICK_MS (default 100ms)
* CONFIG_APP_THERMAL_CUTOFF_TEMP_C (default 85 C)
