## 1. Architectural Philosophy and Design Principles

Traditional embedded firmware development is plagued by three fundamental flaws:
1. "Works on my machine" syndrome caused by fragmented local GCC and SDK installations.
2. Desk-bound testing bottlenecks where verification requires physical microcontrollers, manual jumpers, and bench flashing.
3. Insecure release practices where unsigned binaries are manually emailed or placed on shared drives without checksum manifests.

Our Edge DevOps Pipeline eliminates these failure modes using 4 Core Principles:

* Shift-Left Virtualization: 95% of regressions are caught on pull requests in under 2 minutes using headless QEMU and Renode containers before touching physical hardware.
* Immutable, Containerized Toolchains: Compilers, SDKs, and emulators are packaged as Docker images. No host machine dependencies exist.
* Zero-Trust Cryptographic Release: Binaries are never deployed unsigned. MCUboot cryptographic signatures and SHA-256 manifests are generated in CI.
* Continuous Observability and ChatOps: Prometheus and Grafana track firmware size bloat and HIL pass rates, while Google Chat webhooks broadcast instant alerts.

## 3. The 8-Stage Pipeline Lifecycle

### Stage 1: Containerized Toolchains (zephyr-build-env)
* Implementation: build-env/Dockerfile and build-env/Dockerfile.scratch
* Purpose: Packages Ubuntu 24.04, Zephyr RTOS v3.7.0, ARM Mnu SDK 0.16.8, CMake, Ninja, and Renode v1.17.0.
* DevOps Strategy: Layered container strategy for 45-second local rebuilds and monolithic clean-room disaster recovery.

### Stage 2: CI/CD Pipeline Orchestration
* Implementation: ci-cd/Jenkinsfile and ci-cd/docker-compose.yml
* Purpose: Manages automated build triggers, Docker agent execution, workspace volume mounts, and notifications.
* Polling Trigger: pollSCM('H/2 * * * *') automatically triggers within 2 minutes of a Git push.
* Agent Architecture: Runs as root inside the Docker build container using Docker-in-Docker socket mapping (/var/run/docker.sock).

### Stage 3: Static Analysis and MISRA-C Gate
* Implementation: Cppcheck and Clang-Tidy CLI inside the build container.
* Purpose: Scans C code for buffer overruns, memory leaks, null pointer dereferences, and dead code before compilation starts.
* Exit Code Contract: Executed with --error-exitcode=1 to block bad PRs immediately.

### Stage 4: Fast Smoke Simulation (QEMU Cortex-M33)
* Implementation: simulation/qemu/run_qemu_test.py
* Purpose: Instant verification that the compiled binary boots, the Zephyr kernel starts, and threads schedule properly.
* Speed: Executes in under 3 seconds.

### Stage 5: Full-System Peripheral Emulation (Renode)
* Implementation: simulation/renode/rw610_renode.repl, stm32_simulation.resc, run_renode_test.py
* Purpose: Simulates complete hardware peripherals without physical boards.
* Virtual Mechanics: Models 11 physical GPIO slider contacts (PB0-PB10), Master ON/OFF power button, and motor gate driver.
* Contract: Asserts 9 sequential milestones (soft-start acceleration, steady state RPMs, and safe deceleration).

### Stage 6: Security, Signing and Cloud Storage (MCUboot + AWS S3)
* Implementation: imgtool (Python MCUboot signing tool) and AWS CLI.
* Purpose: Enforces cryptographically signed firmware releases.
* Workflow: Signs release binary with private RSA/ECDSA keys, generates SHA-256 manifests, and uploads to an encrypted AWS S3 release bucket.

### Stage 7: Physical Hardware-in-the-Loop (HIL) Automation
* Implementation: Headless SEGGER J-Link scripts (JLinkExe) and Python pyserial.
* Target Silicon: NXP RW610 Cortex-M33 on custom AzureWave test jig.
* Workflow: Flashes real 8MB Quad-SPI flash over JTAG in 2.5 seconds, captures real silicon serial logs on /dev/ttyUSB0, and verifies motor gate output.

### Stage 8: Dual-Bank A/B OTA, Observability & Google Chat Alerts
* Implementation: 8MB Flash MCUboot partitioning layout, Prometheus, Grafana, and Google Chat Webhooks.
* Rollback Safety: 3.5 MB Slot 0 (Active) and 3.5 MB Slot 1 (Staging) with automated MCUboot rollback protection.
* ChatOps: Instant cards sent to Google Chat upon pipeline completion or failure.

## 5. Observability Architecture: Prometheus and Grafana

Observability is divided into two distinct monitoring domains:

### 5.1 Pipeline & Firmware Resource Observability (DevOps Metrics)
In embedded firmware, **Flash (ROM) and SRAM bloat** is a silent killer. If a developer includes a heavy library that pushes code size past the partition boundary, builds must be flagged immediately.

* **Scraped Metrics:**
  - `firmware_flash_used_bytes`: Tracks binary growth against the 3.5 MB partition budget.
  - `firmware_ram_used_bytes`: Tracks BSS and data memory growth against the 1.2 MB SRAM budget.
  - `pipeline_stage_duration_seconds`: Identifies CI bottlenecks across QEMU, Renode, and HIL.
  - `hil_test_pass_ratio`: Success rate of physical J-Link flashing and silicon boot on the test jig.
* **Grafana Dashboard:** Displays historical size-trend graphs, alerting if any PR consumes more than +50 KB of Flash.

### 5.2 Edge Appliance Fleet Observability (Hardware Telemetry)
In connected commercial kitchens, appliances stream operational metrics back to the cloud via Wi-Fi 6:
* **Appliance Metrics:**
  - `mixer_motor_rpm`: Instantaneous tachometer speed.
  - `mixer_motor_duty_percent`: PWM duty cycle applied to the MOSFET driver.
  - `mixer_motor_temp_celsius`: Motor coil temperature (alerts before 85C cutoff).
  - `mixer_slider_position`: Active mechanical lever contact (PB0-PB10).
* **Alerting Rules:** If `mixer_motor_temp_celsius > 80` for 30 consecutive seconds, Grafana triggers an emergency alert.

## 6. ChatOps: Google Chat Webhook Integration

Whenever a pipeline completes or fails, Jenkins posts an automated interactive card directly to the engineering team's **Google Chat space** using an Incoming Webhook:

1. **Success Notification:**
   * Green verified card displaying Git commit sha, branch, QEMU & Renode verification, and the AWS S3 artifact URI
2. **Failure Alert:**
   * Red warning card identifying the exact failing pipeline stage, CI console log URL, and commit author for immediate rollback.

---

## 7. Quality Gate Policy and Exit Code Contracts

Every stage in this pipeline communicates through deterministic Unix exit codes:
* Exit Code 0: Stage passed. Jenkins marks the stage GREEN and proceeds to the next gate.
* Exit Code Non-Zero (1): Stage failed. Jenkins marks the stage RED, halts execution immediately, prevents downstream flashing, and dispatches a Google Chat alert.
